# Ulnar RPG — Instructions permanentes pour les agents

## Objectif et sources
Développer la V1 joueur d'Ulnar pour alléger la gestion des joueurs et du MJ. Lire PRD.md, ARCHITECTURE.md, TESTING.md, DEVOPS.md, ROADMAP.md, docs/rules/validated-decisions.md et docs/rules/catalog-sources.md avant de modifier le code. Les cinq documents de conception sont historiques : leurs mentions de l'absence de code et du cadrage en attente ne décrivent plus l'état du dépôt. Les décisions métier explicites plus récentes priment. Examiner l'état réel du dépôt, ne pas dupliquer les modules déjà présents.

Les classeurs restent sur la branche privée `feature/ulnar-v1`. Pour les consulter, utiliser cette référence sans ajouter les binaires à une branche de livraison. Sources privées à examiner : docs/references/Fiche Vierge(1).xlsx (référentiel officiel) et docs/references/Nys V3.xlsx (exemple personnalisé, oracle candidat). docs/references/legacy-apps-script.md documente le comportement des scripts fournis et les écarts. Les sources binaires ne doivent jamais être importées par le code frontend, copiées dans public/ ou dist/, ni incluses dans les artefacts de livraison. Ne pas publier le lore, les données personnelles ou les images de Nyssara. Ne diffuser que les contenus joueurs autorisés et dont les droits sont vérifiés. Les fixtures de tests restent hors du build. Ne pas recopier les données personnelles dans les rapports.

## Règles d'architecture
- Conserver TypeScript strict, Vite vanilla, Zod, idb/IndexedDB, HTML sémantique et CSS. Aucun backend métier, framework lourd ou service externe ajouté sans accord. Node 24, npm ci et lockfile. Respecter les modules existants dans src/core, src/data, src/features, src/storage, src/ui; adapter les chemins historiques dans ARCHITECTURE.md au dépôt réel.
- Calculs métier purs, séparés de DOM/stockage; validation runtime des données non fiables; commandes atomiques sans mutation partielle. Ne persister que les sources, pas les valeurs dérivées concurrentes. Versionner le schéma JSON et les règles séparément. Multi-personnage local, imports non destructifs, export et restauration. L'autorisation MJ V1 est manuelle, pas une sécurité serveur.
- Le catalogue officiel est unique et immuable. Extensions personnalisées par personnage, propriétaire contrôlé, identifiants custom: distincts, intégrées dans JSON et IndexedDB. Ne pas remplacer les données officielles par le catalogue de Nyssara.
- Reproduire strictement les formules Excel/Sheets, références et arrondis, même si elles paraissent erronées. Seules les décisions explicites les remplacent. Ne pas déduire arbitrairement les effets textuels, les règles de critiques, les limites ou les comportements non définis. Inventorier les cellules/formules, entrées, dépendances, résultat attendu et test. Les caches Excel sont des observations et non un oracle recalculé. Isoler et signaler chaque règle non reconstructible; poursuivre les lots indépendants. Ne pas masquer un blocage par un zéro, une formule inventée ou un test tautologique.
- V1 : pas de comptes métier, API, synchronisation, espace MJ centralisé, étude des métiers hors premier jet, import automatique Excel, carte interactive ou combat collectif. Le serveur personnel sert des fichiers statiques protégés; aucun déploiement réel sans validation de l'hôte, HTTPS, contrôle de toutes les URLs, sauvegarde et rollback.

## Qualité et livraison
- Ajouter des tests de comportement (unitaires, intégration, E2E) avant ou avec chaque lot. Inclure cas limites, références invalides, données malveillantes, erreurs de stockage, migrations et isolation des personnages. Tester les formules avec des données indépendantes et traçables; Nyssara est un cas parmi d'autres.
- Exécuter npm run format, npm run lint, npm run format:check, npm run typecheck, npm test, npm run build, npm audit; exécuter la couverture et les E2E. Vérifier que le typecheck couvre également les nouveaux tests/configs si possible sans casser le projet. Dans Codex Cloud, utiliser le Chromium système via la configuration cloud validée; si le navigateur épinglé est inaccessible, signaler exactement la différence. GitHub Actions doit continuer à exécuter la CI complète avec Chromium officiel; ne pas désactiver ni affaiblir les checks. Ne jamais annoncer un test non exécuté comme réussi.
- Ne pas écrire directement sur main, ne pas fusionner automatiquement, ne pas force-push. Utiliser la branche de travail et des commits cohérents; préparer une PR de livraison avec preuves, risques, choix et liste des critères non validés. Ne pas manipuler de secrets ni de serveur réel; pas de publication de release/prod ni de tag final sans recette et accord.
- Actualiser README, documentation, ADR, matrice des règles, guide joueur/mainteneur et rapport de recette. Conserver les décisions précédentes et documenter les écarts. Ne pas faire passer un prototype ou un écran vide pour une fonctionnalité terminée.
